# 跨分支能力移植：以 RedAI 为母版

> 目标：把 ARTEX 生态里其他二开分支「RedAI 没有、且可低成本吸收」的能力并入 RedAI，
> 让它在保持自有闭环（goal 闸门 / 证据分级 / 公文级报告）不变的前提下，补齐
> **打点绕防、内网纵深、域攻击、反蜜罐、批量导资产**五块短板。
>
> 原则：①只并「纯 Go / 零外部二进制」的能力；②不改 RedAI 既有语义，只做加法；
> ③每项都要在 CI 里有绑定守卫，漏绑即失败。

## 五、使用建议（给 agent 的纪律）

1. **先判蜜罐再深入**：新资产、异常顺利的目标、异常多端口的主机，先 `honeypot_check`；
   score ≥ 0.6 只做只读验证，≥ 0.9 立即停手并把结论写成 fact。
2. **打点先过 WAF**：`waf_probe` 命中变体后，直接拿穿透手法做后续利用，并在
   `report_finding` 里附上变体与原始响应作为证据。
3. **内网按链路走**：`expand_cidr` → `tcp_probe` → `nbns_probe`（拿主机名/登录用户）
   → `dir_probe` / `subdomain_probe` → `ssh_check` / `smb_check` / `http_login_check`
   验证复用 → 命中即 `record_fact` + `insert_assets`，再考虑下一跳。
4. **凭据先进库、再复用**：发现凭据立刻 `record_credential`（带来源），不要只贴在
   fact 里；要试"这些账号能进哪几台"用 `credential_reuse_matrix`（先 `dry_run=true`
   看范围），它会自动选协议、防锁定、并把成功结果写回 `verified` 关系。
   域内则 `ldap_enum` → `asrep_roast` → `smb_check` 串起来。
5. **凭据状态分两种，别混**：`discovered` 只代表"在某处发现了"，能不能用未知；
   `verified` 才代表"在该资产上认证成功"。报横向移动类漏洞必须以 `verified` 为依据。
6. **跨资产对照用 `auth_request(credential_id=...)`**：凭据登记在 A、要拿它去 B 验证
   越权时，用 `credential_id` 而不是先在 B 上重复登记一份。
7. **资产清单不要手工敲**：甲方给 xlsx/csv，直接 `import_assets_from_file`。
8. **先查资料再动手**：拿到任务先 `knowledge_list` 看有没有甲方给的资料（账号体系、
   网络拓扑、已知限制），动手前 `knowledge_search` 查方法论与历史同类案例。
   从目标机取回的配置/日志用 `knowledge_add` 整篇入库（**存原文，不要先摘要**——
   IP、路径、报错码是检索时才需要的关键字）；写全局库只有 planner 与人类主控能做，
   worker 一律写任务库。报告里引用知识库结论要带 `source_ref`，别凭记忆复述。
9. **先指纹、再查 CVE**：探到 Web 服务后先 `web_fingerprint`，拿 `next_queries` 直接
   喂 `search_vulns`，别凭首页印象猜组件版本；版本拿不到就按 product 查完用
   `get_vuln` 看 CPE 区间，不要自己凑版本号。路径类结论以 `evidence` 为准。
